# E32 — candidate source and provenance results

Date: 2026-10-29. This phase inspected public GitHub repository metadata, pinned commits, source trees, license files and selected API/build files. No candidate build script was executed, no candidate APK/AAR/JAR was loaded into Fonesi, and no third-party binary was imported.

## Decision

**NO-GO: no new provider qualifies for production integration on the evidence collected.** One additional candidate, WaxMoon/MultiApp, has a documented directory-based API for APK/split sets, but the core engine is delivered as an opaque `moon.jar` and the project says the repository is no longer maintained. Another recent-looking VirtualApp fork bundles an opaque release AAR and has no verified license/provenance record in the inspected repository metadata. These do not resolve the engine blocker.

## Key finding

WaxMoon's API is the first new source examined in this gate that explicitly documents installation from a directory containing split APKs. However, the API calls an opaque `moon.jar` engine through a command bridge, and the source repository itself says it is no longer maintained. The key production behavior cannot be audited or reproduced from the visible source tree. This is **a lead for source/provenance acquisition, not a green-light to integrate**.

## Next smallest useful action

E33 should be a source-acquisition gate, not another synthetic app proof:

1. Seek the full source/build inputs and native dependency inventory for WaxMoon's `moon.jar`, plus confirmation of the exact AGPL-3.0 obligations and whether the intended product distribution model can comply.
2. Seek source, license and reproducible build provenance for ServenScorpion's `lib-release.aar` if that fork remains of interest.
3. If neither provider can supply the missing evidence, keep the NO-GO decision and evaluate a first-party engine architecture or a licensed provider with an explicit split/component/isolation contract. Do not import either opaque binary.
