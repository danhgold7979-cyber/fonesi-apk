## E21 strict implementation plan

1. Add `scripts/build_isolated_split_fixture.py`: use pinned SDK36 `aapt2`, `javac`, `d8`, `apksigner` plus disposable 2048-bit RSA test key to assemble **two independently signed APKs with identical signer, package, version**: base `vn.fonesi.splitfixture` and isolated feature `feature.alpha`. Base and feature each have a tiny independent Java method and independent synthetic resource marker. No INTERNET, dangerous permissions, real accounts, native .so, spoof or external secrets. Hash files and verify signatures. No production key generated or committed. Explicit `android:isolatedSplits=true` is required in base. Android PackageManager must actually accept `adb install-multiple` and report both paths; otherwise FAIL.
2. Add `engine-source/IsolatedSplitCodeProbeLoader.kt`: test-only opt-in, restricted to signed `vn.fonesi.splitfixture` and dedicated `:fonesi_guest_split` process with native routing ENABLED, worker thread, 64-bit ABI, one attempt per process. Verify/read `PrivateApkStore` cluster; compute `GuestSplitGraphPlanner`; construct a fresh `DexClassLoader` for the base and each feature with parent from the verified DAG, *not* a flattened classloader. Use only canonical private APK paths; prepare native path with existing verifier. Attempt Resources via private source paths using the public `PackageManager.getResourcesForApplication(ApplicationInfo)` path; **no fallback to the installed original resources**. Recheck private bytes after loading.
3. Add separate internal `SplitCodeProbeService` and explicit test `SplitCodeProbeActivity`, with dedicated `:fonesi_guest_split` process, signed PackageManager readback of installed fixture's base/feature/signer, private publication and exact split graph check. Actual Dex loader must execute BaseEntrypoint and FeatureEntrypoint bytecode from private APKs and validate fresh challenge response. Base loader must NOT load feature class, host classloader must load neither. Verify base/feature resources from private source or fail; record distinct flags `private_isolated_base_code_executed`, `private_isolated_feature_code_executed`, `private_isolated_resources_verified`, `private_split_graph_verified`.
4. Extend `run_guest_code_emulator.py` `--proof-level e21`: require four APKs (existing probe/payload and new split base/feature), check exact SHA-256 for each, fresh AOSP34 x86_64 KVM AVD, install two-APK fixture via `adb install-multiple`, launch only explicit test Activity. Accept only a fresh UUID-bound report, real private classloader and resource assertion flags; retain signed fixture and sanitized receipts.
5. Update exact component allowlist for probe manifest (4 exported test Activities, 5 non-exported internal guest services), narrow manifest package visibility to exactly the two project-owned synthetic packages; no permissions granted and no existing E11–E17 acceptance assertions weakened.
6. Pinned GitHub Actions E21: signed fixture generator, compile/lint/source-native/JVM tests and AOSP34 emulator with bounded timeout. If install, classloader or resource loading fails, **record FAIL and exact stage**. Do not call plan/DEX class only a full split runtime PASS. Diagnose and correct code after observing actual CI logs. Do not replace private bytes with installed APK fallback.
7. Report results; even a PASS is only **synthetic isolated base + one feature**. Multiple feature dependencies, dynamic splits/Play Store, resource classloader edge cases, arbitrary third-party Activities/Services/Providers/Binder, security isolation, Android ARM64/Samsung, phone performance and social-account compatibility remain future gates.

## End-user product boundaries

- The user-facing `0.5.0-candidate` SpaceCore is still **single APK, ARM64/API26–34/4KB** and `importsSplitApks=false`. No production capability or release artifact is upgraded by E21.
- Running multiple guest-named processes under one host UID is not Android kernel-level isolation; never claim real account secrets are safely separated from untrusted code.
- Never install on user phone, send passwords/OTP, force-push/merge `main`, re-sign third-party APKs, hide test failures, or use private original APK classes as fallback.
