## Decision and hard incompatibility

**No candidate is eligible for activation on the evidence examined.** A same-UID namespace is not an acceptable stronger isolation mode for hostile guest access. SEC-003–007/060 and BRG-003 remain mandatory: allowing arbitrary third-party native code to run with the manager's unrestricted UID/filesystem authority cannot be repaired by labeling directories, IDs or UI rows differently. A claimed capability or successful unit truth table is not platform attestation. This is a hard mismatch for that proposed boundary, not a proof that every possible no-root architecture is impossible.

Android's documented application sandbox relies on kernel-enforced UID/process security and covers native code. **Inference for this design:** naming a second directory inside the same security principal cannot create that independent OS boundary. Any stronger mediation proposal must first present its actual enforceable boundary and adversarial proof; caller-supplied flags cannot qualify it. [Android sandbox](https://source.android.com/docs/security/app-sandbox)

An Android isolated-process service is documented as a restricted process without its own permissions, exposed through service communication. **Inference:** it is a useful primitive to evaluate, not an automatic guest Android installation, Activity stack, services/providers/notifications broker or eight-app compatibility solution. An unrestricted broker could undo separation; every privileged channel needs scoped authorization and testing. [Android service contract](https://developer.android.com/guide/topics/manifest/service-element)

A separate guest OS/VM may change the boundary, but has unresolved platform availability, memory/storage, framework, signing/identity, notification, source/licensing and UX constraints. Switching to root, limited work profiles, altered third-party identities or a reduced app list is not authorized by this plan. Do not promise every mandatory app will work. Native API26/target36 compilation does not establish any of those facts.

## Minimal evidence package before any candidate activation

1. Full immutable source revision; exact artifact SHA256; complete dependency/native SBOM with origins, licenses and reproducible build recipe. No unexplained binary-only engine, telemetry, identity substitution, crash suppression or dynamic remote rule acquisition.
2. Explicit boundary diagram: manager, broker, guest A/B, original app and Android services. Record actual UID/process/SELinux or guest-OS principals, every shared channel, accessible files, inherited handles and authority owner. A separate process name is insufficient.
3. Versioned capability snapshot bound to provider ID/revision/dependency digest and actual API/ABI/page-size environment. Unknown values disable operations. Changed identity/environment invalidates receipts; no caller-set readiness as authority.
4. Typed signed-cluster preflight/install/private inspect interfaces; exact package/version/signer lineage/member digest/split graph/native ABI identity; no original-app fallback. Operation result discriminates verified success, proven no-change, proven rollback, deferred, unsupported, security rejection and ambiguous review-required.
5. Scoped live foreground auth, exact provider handle/generation/complete affected peers, durable intent before dispatch and independent postcondition readback. Interruption cannot silently duplicate updates or discard retained source.
6. Owned synthetic test plan below executed under an authorized runtime after source review. Only after synthetic isolation/lifecycle gates pass may the owner install a PoC and manually use owned test accounts. Four phone gates and eight separate app results remain required.
