# Public-API feasibility follow-through — 2026-11-01 11:13 UTC

**Research only. No provisioning, policy mutation, APK acquisition/installation, permission change or execution.** This analysis separates a documented route from a proven product capability. Existing scope remains active; V2 agreement and review are pending.

## A. Installed-original signed base/split transport

**Documented building blocks exist; end-to-end secure route NOT PROVEN.**

1. Personal-side discovery can obtain package metadata within visibility rules. `ApplicationInfo.sourceDir` and split paths identify installed files; `publicSourceDir` may expose only publicly available resources/manifest for forward-locked applications. A path field is not a guarantee of readable full APK bytes. Snapshot only actually readable complete original base/splits; verify membership, signing lineage, sizes/hashes and consistency before/after copy. Otherwise report `SOURCE_UNREADABLE`/`SOURCE_CHANGED` with zero installer dispatch. No broad storage grant, downloaded replacement or copied account/session fallback. [ApplicationInfo](https://developer.android.com/reference/android/content/pm/ApplicationInfo#publicSourceDir)
2. Android documents cross-profile **content URI** sharing; file URIs do not work as cross-profile file identities. The DPC can add directional cross-profile **activity-intent** filters; this is not a generic service/Binder channel. A proposed route is a narrowly filtered, explicit user-visible transfer activity and read-only temporary grants to immutable owned source snapshots. Resolve actual profile/handler, bind operation and cluster digest, expire/revoke access, and reject arbitrary path/write/foreign-profile requests. Mere successful intent resolution does not authenticate the ultimate recipient or prove target-profile installation. [Work-profile sharing](https://developer.android.com/work/managed-profiles#share_files_across_profiles), [DPM intent filters](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#addCrossProfileIntentFilter(android.content.ComponentName,%20android.content.IntentFilter,%20int))
3. **New trap:** API30 `CrossProfileApps.canRequestInteractAcrossProfiles()` explicitly requires the requesting package NOT to be a profile owner in the profile group. Its arbitrary-activity route also has cross-profile consent/allowlisting restrictions. Therefore the single-package DPC cannot be assumed to request this grant to itself. API28 main-activity switching is not a general data-transfer API. Do not add a companion package, self-grant permission or privileged alternative silently; such design would need its own scope/security review. The candidate above remains the separately documented activity-filter/content-URI route, subject to actual authentication/grant tests. [CrossProfileApps](https://developer.android.com/reference/android/content/pm/CrossProfileApps#canRequestInteractAcrossProfiles())
4. On the work side, stage verified complete unchanged signed members into one profile-local PackageInstaller session. Account for pending user action, installer/update ownership, policy denial and cancellation. `setRequireUserAction(NOT_REQUIRED)` does not establish authority or guarantee no prompt; the initial design must handle user confirmation and must not expand permissions for silent install. An install-success callback is followed by independent profile-local package/signer/member readback. [SessionParams](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)), [PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller)

**Necessary security proof:** which principal receives the URI grant through the OS forwarder; caller authentication at both ends (never trust a caller-supplied package/profile); no same-package impersonation by another signer; no malicious resolver/handler; revoked/expired grant; stale profile serial/generation; digest mismatch or member omission; process death during copy/commit; locked profile; no personal fallback. Cross-profile origin authentication cannot be asserted merely from an exported activity's intent extras. If an authenticated narrow transport cannot be established, source import remains unsupported.

**Source-update race:** external stores or OS installers may replace the original at any moment. Revalidate complete source generation before commit and inspect actual installed state afterward. An earlier original snapshot is not fresh authorization. Same-version import is not automatically harmless to other profiles/processes; actual PackageInstaller behavior and complete impact still need measurement.

## B. Complete shared-code update scope

**No supported ordinary-BYOD public route establishing complete device-wide affected installations was identified in this pass. This is a genuine blocking gap, not implementation-ready scope.**

`UserManager.getUserProfiles()` returns users associated with the current context (and excludes restricted profiles); `LauncherApps.getProfiles()` is limited to profiles accessible to the caller. Neither contract promises arbitrary device-user enumeration. Cross-user operations have privileged permission/role constraints. The documented AOSP multi-user test commands are test/ADB facilities, not application authority and are explicitly excluded from the product route. [UserManager](https://developer.android.com/reference/android/os/UserManager#getUserProfiles()), [LauncherApps](https://developer.android.com/reference/android/content/pm/LauncherApps#getProfiles()), [AOSP multiple-user testing](https://source.android.com/docs/devices/admin/multi-user-testing)

App code updates may affect both personal and work installations. Thus two visible rows do not prove the consented set is exhaustive. Even a user's statement that no other profile exists is not the required independent platform readback. No hidden API, root, ADB user enumeration, device-owner conversion or broad privileged permission is an acceptable fallback. [Google update guidance](https://support.google.com/work/android/answer/9350374?hl=en)

Current consequence: `COMPLETE_SHARED_SCOPE_UNKNOWN` must keep Fonesi-initiated updates disabled on such a device. An exact device configuration with stronger independently supported evidence may be evaluated, but a single emulator setup must not become a broad consumer-phone guarantee. A new requirement allowing explicit known/unknown shared impact, or delegating all updates to OS/store, would be a **material scope change requiring owner agreement**, not a fix already authorized by “continue”. Neither is adopted here.

External OS updates/uninstalls/profile removal remain possible while Fonesi is locked/backgrounded. They trigger snapshot/consent/capability invalidation and reconciliation, never automatic replay or a false claim of manager enforcement. Version/marker checks after an external update can record observations but cannot retroactively invent Fonesi consent.

| Item | Present result | Permitted next proof | Not implied |

| Readable installed original full cluster | Conditional, app/device dependent | Owned signed fixtures and strict snapshot tests | All eight app sources readable |

| Actual app compatibility | Eight UNKNOWN | Separate later authorized phone/accounts after safety gates | Production success from documentation |

Independent source work that does not choose this architecture remains possible: original style/schema/codec and pure signed-cluster validation logic with host-only tests, no Android dispatch. Such work must retain its original task mapping and cannot be relabeled as completed V2 runtime.
